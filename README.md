# Robot Control: Raspberry Pi 4 ↔ Windows

- **robot** — консольный сервер на Raspberry Pi OS (Linux) или Windows: принимает команды по TCP, отправляет телеметрию и видео; на Raspberry Pi управляет двумя сервоприводами камеры через аппаратный PWM и передаёт команды колёс на ESP32 через GPIO UART.
- **control** — существующее приложение Qt6 для Windows: управление клавиатурой/мышью, видео и HUD.

На Raspberry Pi используется камера **IMX219, индекс 0**, через `rpicam-vid`. По умолчанию: **1280×720, 30 fps, H.264, 4 Мбит/с**. Эти параметры относятся к выходному видео; режим сенсора из списка `--list-cameras` выбирает стек камеры. В этой реализации выход ограничен 1920×1080 и 30 fps.

Передача команд колёс включается параметром `--drive-uart`; без него команды движения только выводятся в консоль. Телеметрия использует доступные датчики Linux; отсутствующие показания передаются как `NaN`. Сервоприводы камеры работают при запуске с `--servos` после настройки PWM, описанной ниже.

## Структура проекта

```
common/      контракты между двумя машинами: ноутбук <-> расба (protocol.h)
control/     пульт: приложение Qt6 на Windows
robot/       всё, что исполняется на роботе
cmake/       поиск GStreamer
third_party/ SDK лидара LDROBOT
tests/       модульные тесты и интеграционный тест UART
```

Внутри `robot/` три уровня — сверху вниз: что робот решает, затем из чего он
сделан.

```
robot/
  main.cpp            сборка и запуск: по потоку на систему, и всё
  state.h             доска: слоты, через которые потоки обмениваются данными
  control_loop.cpp    ЕДИНСТВЕННОЕ место, которое командует приводом и сервами

  control/            КАК ехать
    manual/teleop.*     ручной режим: команда оператора идёт как есть
    auto/slam.*         SLAM: поза и карта по одному лидару
    auto/explore.*      политика: ехать к ближайшей неисследованной клетке
    safety/             гейт препятствий и пороги секторов

  supervisor/         ЧТО пришло и что с этим делать
    intents.h           валидация кадра -> намерение оператора
    recovery.*          автомат потери связи: стоп, пауза, короткий откат, стоп

  systems/            ЧЕМ робот обладает
    rpi/                код, исполняющийся на расбе
      lidar/ drive/ servos/ camera/ link/ logging/ health/
      link/map_link.*     канал карты и режима, порт 5004
    esp32/              нижний уровень привода
      uart_protocol.h     контракт линии расба <-> ESP, общий для обеих сторон
      motor_driver/       прошивка ESP32
```

Правило зависимостей — только вниз: `control_loop` → `control` → `supervisor` →
`systems`. `systems/rpi/link` не знает, что означает принятый кадр; `control` не
знает про сокеты. Поэтому автономное управление добавляется как второй источник
`DriveCommand` прямо перед гейтом безопасности, и всё, что ниже — гейт, UART,
манёвр при потере связи — продолжает работать без изменений.

Протокол расба ↔ ESP32 лежит **внутри** робота, а не в `common/`: `common` — это
граница между двумя машинами, а обе стороны UART стоят на одном роботе.
Подробности — в [`robot/systems/esp32/README.md`](robot/systems/esp32/README.md).

## Сборка на Raspberry Pi

Скопируйте весь каталог исходников, включая `common/` и `cmake/`. Используйте новый каталог `build-pi`: имеющийся `build/` содержит Windows-бинарники и Windows CMake cache.

Если после старой конфигурации `build-pi/robot` уже является каталогом, используйте свежий каталог сборки, например `build-pi-fixed`, во всех командах сборки и запуска. Новая конфигурация размещает служебные файлы подпроекта в `robot-build`, отдельно от исполняемого файла `robot`.

Из корня проекта на Raspberry Pi OS с установленным стеком `rpicam`:

```bash
sudo apt update
sudo apt install -y build-essential cmake pkg-config libgstreamer1.0-dev \
  gstreamer1.0-tools gstreamer1.0-plugins-base gstreamer1.0-plugins-good \
  gstreamer1.0-plugins-bad rpicam-apps

cmake -S . -B build-pi -DCMAKE_BUILD_TYPE=Release -DBUILD_CONTROL=OFF
cmake --build build-pi -j2
```

На Linux `BUILD_CONTROL` по умолчанию уже выключен. Qt, Visual Studio и Winsock для сервера не нужны. Требуются C++17, CMake 3.21+ и pthreads.

Альтернативная сборка только из подпроекта (также используйте свежий каталог):

```bash
cmake -S robot -B build-pi-server -DCMAKE_BUILD_TYPE=Release
cmake --build build-pi-server -j2
```

## Запуск Raspberry Pi → Windows

1. На Raspberry Pi проверьте камеру и узнайте адрес устройства:

   ```bash
   rpicam-hello --list-cameras
   hostname -I
   ./build-pi/robot
   ```

2. На Windows запустите `control.exe`, пересобранный с текущим `common/protocol.h`. В поле **IP** введите IPv4-адрес Raspberry Pi, например `192.168.1.50`. Порты: **cmd 5001**, **tlm 5002**, **video 5003**. Нажмите **Connect**.
3. Сервер получает IP Windows из входящего соединения команд и начинает отправлять видео на этот адрес. До подключения клиента камера не запускается. При разрыве канала команд автоматическая передача видео останавливается; при новом подключении запускается снова.
4. Ожидаемые признаки: в консоли Raspberry Pi появляются подключения и изменения команд; Windows показывает видео, температуру CPU и заряд при наличии драйвера батареи. Недоступные показания в HUD отображаются как `--`.

Неиспользуемый массив точек лидара заменён шестью секторными вердиктами, и размер пакета стал **22 байта** (был 160). Сервер и Windows-клиент нужно пересобрать с одним `common/protocol.h`: клиент со старым размером потеряет границы пакетов. Согласования версии по TCP нет. Изменения исходников не обновляют уже лежащие в `build/` исполняемые файлы.

Если Windows блокирует входящее видео, разрешите `control.exe` в брандмауэре для частной сети либо выполните в PowerShell **от администратора**:

```powershell
New-NetFirewallRule -DisplayName "Robot Control video" -Direction Inbound -Action Allow -Protocol UDP -LocalPort 5003 -Profile Private
```

На Raspberry Pi должны быть доступны входящие TCP 5001/5002; Windows принимает UDP 5003. IP Windows и IP Raspberry Pi выполняют разные роли: Windows подключается к Raspberry Pi, Raspberry Pi отправляет видео обратно на Windows.

## Параметры сервера

```bash
./build-pi/robot --help
./build-pi/robot --camera 0 --width 1920 --height 1080 --fps 30 --bitrate 4000000
./build-pi/robot --video-host 192.168.1.100 --video-port 5003
./build-pi/robot --command-port 6001 --telemetry-port 6002 --video-port 6003
./build-pi/robot --video-source none
```

| Параметр | По умолчанию | Значение |
|---|---|---|
| `--command-port` | 5001 | TCP-порт приёма команд |
| `--telemetry-port` | 5002 | TCP-порт выдачи телеметрии |
| `--video-port` | 5003 | UDP-порт Windows-приёмника |
| `--video-host` | автоматически | Фиксированный IPv4 получателя видео |
| `--video-source` | `camera` | `camera`, `test` или `none` |
| `--camera` | 0 | Индекс камеры для `rpicam-vid` на Linux |
| `--width`, `--height` | 1280, 720 | Чётные размеры выходного кадра, до 1920×1080 |
| `--fps` | 30 | Частота выходного видео, 1–30 |
| `--bitrate` | 4000000 | Битрейт H.264 в битах/с |
| `--drive-uart` | выключен | Включить передачу команд колёс через UART, только Linux |
| `--drive-uart-device` | `/dev/serial0` | Устройство UART |
| `--drive-uart-baud` | 115200 | Скорость UART: 9600, 19200, 38400, 57600, 115200 или 230400 бод |

Фиксированный `--video-host` включает передачу сразу, даже без TCP-клиента. Без него получатель определяется только по соединению команд. Номер UDP-порта по TCP не передаётся: при его изменении выставьте то же значение в окне Windows. TCP-порты команд и телеметрии должны отличаться.

Для тестовой картинки вместо камеры:

```bash
sudo apt install -y gstreamer1.0-plugins-ugly
./build-pi/robot --video-source test
```

`test` использует `videotestsrc` и доступный H.264-кодировщик; пакет `plugins-ugly` даёт `x264enc`. В режиме `camera` Linux-сервер использует H.264 из `rpicam-vid`, дополнительный программный кодировщик GStreamer ему не нужен. Ошибка камеры выводится в консоль с повторной попыткой запуска; тестовая картинка автоматически не подставляется.

`Ctrl+C` или `SIGTERM` завершают сервер, закрывают сокеты и останавливают дочерний `rpicam-vid`. Ошибка запуска TCP-слушателя завершает сервер с ненулевым кодом; ошибка видео оставляет каналы команд и телеметрии работающими.

## Команды колёс: Raspberry Pi 4 → ESP32 через GPIO UART

Сервер преобразует `direction` и `speed` из команды ноутбука в целые проценты правого (`R`) и левого (`L`) колёс. `speed` имеет диапазон 0…1; `P = round(speed × 100)`. Положительный процент означает движение колеса вперёд, отрицательный — назад, ноль — остановку.

| Команда ноутбука | Правое колесо R | Левое колесо L | Пример при speed = 0.5 |
|---|---|---|---|
| `STOP` | 0 | 0 | `R:0%\|L:0%` |
| `FORWARD` | P | P | `R:50%\|L:50%` |
| `BACKWARD` | −P | −P | `R:-50%\|L:-50%` |
| `LEFT` | P | −P | `R:50%\|L:-50%` |
| `RIGHT` | −P | P | `R:-50%\|L:50%` |

Повороты выполняются на месте. Текущий протокол ноутбука передаёт одно направление и общую скорость: отдельной команды для движения по дуге с разными положительными процентами, например `R:100%|L:50%`, в нём нет.

Параметры линии: **115200 бод, 8N1**, без управления потоком. Каждый полный корректный TCP-пакет порождает ASCII-строку, включая повторы одинаковой команды. В текущем `common/protocol.h` задан период 5 мс (`COMMAND_PERIOD_MS`); для ранее собранного клиента период зависит от его версии. Строка заканчивается одним байтом LF (`\n`), без CR и без завершающего NUL. Например:

```text
R:100%|L:-100%\n
```

В примере `\n` обозначает байт перевода строки, а не два печатных символа. Диапазон каждого колеса — от −100 до 100%. Ответы и подтверждения ESP32 сервер не читает. Существующий приёмник находится в `robot/systems/esp32/motor_driver/motor_driver.ino`; доработка сервера Raspberry Pi не меняет эту программу.

Контракт ESP32: UART RX — GPIO9, TX — GPIO10; сигнал правого ESC (`R`) — GPIO4, левого (`L`) — GPIO5. Эти номера относятся к ESP32. В приёмнике правый ESC инвертирован (`RIGHT_DIRECTION = -1`), левый — нет: знак команды описывает направление колеса, а фактическое направление требует проверки на установленной механике.

Подключение Raspberry Pi 4:

| Raspberry Pi | Физический контакт | ESP32 |
|---|---|---|
| GPIO14 / TXD | 8 | GPIO9 / RX |
| GND | например, 6 | GND |
| GPIO15 / RXD | 10 | GPIO10 / TX, необязательно: ответы не используются |

Используйте сигнальные уровни **3,3 В TTL**, общую землю и свободный UART ESP32. Линии GPIO нельзя подключать к RS-232 или сигналам 5 В. Назначение GPIO14/15 и уровни UART описаны в [документации Raspberry Pi](https://www.raspberrypi.com/documentation/computers/configuration.html#configure-uarts).

Однократно выполните на Raspberry Pi:

```bash
sudo raspi-config
```

Выберите **Interface Options → Serial Port**: доступ к login shell через serial — **No**, включение serial port hardware — **Yes**, затем перезагрузите устройство. Эта настройка освобождает основной UART от системной консоли. [Официальная инструкция](https://www.raspberrypi.com/documentation/computers/configuration.html#disable-the-linux-serial-console).

```bash
sudo reboot
# После перезагрузки:
readlink -f /dev/serial0
ls -l /dev/serial0
```

`/dev/serial0` указывает на основной UART; фактическое имя зависит от настройки Raspberry Pi. Пользователю нужны права чтения и записи в это устройство. В Raspberry Pi OS обычно достаточно добавить пользователя в группу `dialout` и заново войти в систему:

```bash
sudo usermod -aG dialout "$USER"
```

После копирования обновлённых исходников соберите и запустите сервер. Для управления колёсами без камеры:

```bash
cmake -S . -B build-pi-fixed -DCMAKE_BUILD_TYPE=Release -DBUILD_CONTROL=OFF
cmake --build build-pi-fixed -j2
./build-pi-fixed/robot --video-source none --drive-uart
```

Для камеры, её сервоприводов и колёс одновременно, после настройки PWM из следующего раздела:

```bash
sudo ./build-pi-fixed/robot --camera 0 --servos --drive-uart \
  --drive-uart-device /dev/serial0 --drive-uart-baud 115200
```

Здесь `sudo` также даёт необходимые права на PWM. Для UART дополнительные библиотеки не нужны. В Windows режим `--drive-uart` недоступен.

При открытии UART сервер отправляет `R:0%|L:0%\n`. Такая же остановка отправляется при разрыве соединения, некорректной команде, отсутствии полной команды 500 мс и штатном завершении (`Ctrl+C`/`SIGTERM`). При ошибке UART сервер пытается отправить остановку и завершается с ненулевым кодом; дедлайн записи — 100 мс. Если предыдущая запись оборвалась или в очереди остались байты, перед остановкой очередь сбрасывается и добавляется LF для отделения незавершённой строки. Приёмник должен игнорировать пустые и некорректные строки.

Успешная запись означает передачу данных драйверу UART, без подтверждения исполнения на ESP32. При обрыве провода, потере питания Raspberry Pi или `kill -9` отправка остановки не гарантируется. Существующий приёмник ESP32 имеет собственный таймаут: через 500 мс без корректной полной строки с LF оба ESC возвращаются в нейтраль 1500 мкс. Неполные и некорректные строки не обновляют этот таймер. Поэтому одинаковую команду нужно повторять с интервалом меньше 500 мс; например, 50 мс, либо 5 мс, как в текущем исходнике клиента. Таймаут проверяется в основном цикле ESP32, с его обычной задержкой выполнения.

При потере связи с ноутбуком после хотя бы одной корректной команды, если включён `--drive-uart`, сервер выполняет один манёвр:

1. Сразу после обнаружения разрыва TCP или таймаута полной команды 500 мс отправляет STOP.
2. Выдерживает **1 секунду с момента отправки STOP**.
3. Отправляет назад **20% на 300 мс** (`R:-20%|L:-20%\n`), повторяя команду каждые 50 мс для таймаута приёмника ESP32.
4. Снова отправляет STOP и остаётся на месте, ожидая подключения. Манёвр сам по себе больше не повторяется.

Новое TCP-подключение принимается во время любого этапа и сразу отменяет манёвр: если робот уже отъезжает, сначала отправляется STOP, затем принимаются новые команды. Без полной корректной команды новое соединение не запускает следующий отход при отключении. При запуске без клиента, некорректной команде, ошибке оборудования или завершении сервера отход назад не выполняется.

Параметры заданы константами `kPause`, `kReverseDuration` и `kReverseSpeed` класса `DisconnectRecovery` в `robot/supervisor/recovery.h`; сам манёвр выполняет `robot/control_loop.cpp`. Длительность и мощность задают короткий импульс движения, а не точное расстояние: фактический путь зависит от двигателя, покрытия и нагрузки и требует проверки на роботе.

Проверка преобразования команд и передачи через виртуальный UART на Linux (нужны `python3` и `g++`):

```bash
python3 tests/test_drive_uart.py
```

Тесты используют PTY и TCP и не требуют ESP32; они не проверяют физические GPIO, проводку или вращение колёс.

## Сервоприводы камеры на Raspberry Pi 4

Поддерживаются два обычных позиционных RC-сервопривода с управлением длительностью импульса. Для сервоприводов непрерывного вращения этот режим не задаёт угол: у них импульс управляет скоростью.

Подключение сигналов по выбранной схеме:

| Ось | GPIO, нумерация BCM | Физический контакт разъёма | PWM-канал |
|---|---|---|---|
| Pitch, вверх/вниз | GPIO12 | 32 | 0 |
| Yaw, влево/вправо | GPIO13 | 33 | 1 |
| Общая земля | GND | например, 34 | — |

Подайте питание на сервоприводы от отдельного источника с напряжением по их спецификации. Соедините землю этого источника, землю сервоприводов и GND Raspberry Pi. GPIO12/13 подключаются только к сигнальным проводам.

Однократно добавьте в конец `/boot/firmware/config.txt`:

```ini
[all]
dtparam=audio=off
dtoverlay=pwm-2chan,pin=12,func=4,pin2=13,func2=4
```

Эта настройка назначает GPIO12/13 двум аппаратным PWM-каналам. `audio=off` отключает штатное аналоговое аудио, использующее PWM-ресурсы. [Схема официального overlay](https://github.com/raspberrypi/linux/blob/rpi-6.12.y/arch/arm/boot/dts/overlays/pwm-2chan-overlay.dts), [справочник параметров](https://github.com/raspberrypi/linux/blob/rpi-6.12.y/arch/arm/boot/dts/overlays/README).

Перезагрузите Raspberry Pi:

```bash
sudo reboot
```

После копирования обновлённых исходников соберите и запустите из корня проекта:

```bash
cmake -S . -B build-pi-fixed -DCMAKE_BUILD_TYPE=Release -DBUILD_CONTROL=OFF
cmake --build build-pi-fixed -j2
sudo ./build-pi-fixed/robot --camera 0 --servos
```

`sudo` здесь нужен для записи в `/sys/class/pwm`. `pigpio`, `pigpiod` и дополнительные библиотеки не требуются. Без `--servos` сервер не обращается к PWM и работает как раньше. Windows-клиент и формат пакетов сохранены: запустите прежний `control.exe`, подключитесь, нажмите левую кнопку мыши над видео для захвата курсора и двигайте мышь.

Сервер находит PWM0 по узлу устройства `pwm@7e20c000`; номер `pwmchipN` не зафиксирован. При необходимости путь можно задать явно:

```bash
sudo ./build-pi-fixed/robot --camera 0 --servos --servo-pwm-chip /sys/class/pwm/pwmchip0
```

В этом примере `pwmchip0` нужно заменить на контроллер GPIO12/13 вашего устройства. Посмотреть соответствие можно командой:

```bash
ls -l /sys/class/pwm/pwmchip*/device/of_node
```

Импульсы формируются аппаратным контроллером с периодом 20 мс (50 Гц). Программа меняет только их длительность при получении нового положения. Настройки каждой оси по умолчанию используют максимальный разрешённый диапазон: `-1 → 500 мкс`, `0 → 1500 мкс`, `+1 → 2500 мкс`. Угол в градусах зависит от модели и механики. [Интерфейс PWM ядра Linux](https://docs.kernel.org/driver-api/pwm.html).

Отдельная настройка осей, пример со значениями по умолчанию:

```bash
sudo ./build-pi-fixed/robot --camera 0 --servos \
  --pitch-min-us 500 --pitch-center-us 1500 --pitch-max-us 2500 \
  --yaw-min-us 500 --yaw-center-us 1500 --yaw-max-us 2500
```

- `--pitch-invert` и `--yaw-invert` меняют направление соответствующей оси.
- `--pitch-channel 1 --yaw-channel 0` меняют оси местами без перестановки проводов.
- Пределы задаются в микросекундах: `500 ≤ min < center < max ≤ 2500`. Подбирайте их по характеристикам сервопривода и механическим ограничениям крепления.
- До первого корректного пакета команды PWM выключен. Полученные значения являются абсолютным положением: повтор одного пакета не продолжает поворот.
- При разрыве TCP, отсутствии полной команды 500 мс или некорректной команде выдача импульсов прекращается. После переподключения первый корректный пакет снова задаёт положение. Отключение импульсов не снимает питание и не гарантирует удержание камеры.
- При штатном завершении отключаются и освобождаются только PWM-каналы, экспортированные сервером. Уже занятые каналы сервер не перенастраивает; ошибка PWM при включённом `--servos` завершает сервер с сообщением в консоли.
- При `kill -9` или аварии процесса очистка не выполняется: аппаратный PWM может продолжать выдавать последний сигнал.

Если сервер сообщает, что `pwm0`/`pwm1` уже экспортирован, остановите программу, которая им владеет. После аварийного завершения предыдущего сервера перезагрузка Raspberry Pi освобождает его старые экспорты.

## Как передаётся камера

```text
IMX219 → rpicam-vid (H.264) → pipe → fdsrc → h264parse
       → rtph264pay (PT=96) → UDP → Windows control
```

`rpicam-vid` использует аппаратное H.264-кодирование при его наличии и умеет выдавать поток в stdout; на Raspberry Pi 4 это позволяет использовать штатный стек камеры без захвата CSI-сенсора как USB-вебкамеры. [Документация Raspberry Pi](https://www.raspberrypi.com/documentation/computers/camera_software.html#rpicam-vid).

Сервер задаёт `--inline` и ключевой кадр раз в секунду. `rtph264pay config-interval=-1` повторяет SPS/PPS с каждым IDR, чтобы Windows мог начать декодирование после подключения. Передаются **RTP/H.264, PT 96, 90 кГц**, которые уже ожидает `control`. [Документация rtph264pay](https://gstreamer.freedesktop.org/documentation/rtp/rtph264pay.html).

## Реальная телеметрия

Каждые 100 мс сервер заново читает доступные системные датчики. Ошибка чтения, исчезновение устройства или некорректное значение дают `NaN`, без сохранения старого показания и без генерации случайных данных.

| Поле | Источник и смысл |
|---|---|
| `cpu_temp` | `/sys/class/thermal/thermal_zone*/temp`, в градусах Celsius после деления на 1000. Выбираются зоны типа `cpu-thermal`, `cpu_thermal`, `bcm2835_thermal`; при нескольких исправных зонах используется максимальная температура CPU. |
| `battery_level` | `capacity` единственного подходящего устройства `/sys/class/power_supply/*` с `type=Battery`, 0…100%. Устройства с `scope=Device` и отсутствующие батареи (`present=0`) исключаются. Если подходящих батарей несколько или драйвер не предоставляет корректный процент — `NaN`. |
| `sectors[6]` | Вердикт по каждому сектору: `Unknown`/`Green`/`Yellow`/`Red`. Реального драйвера лидара пока нет — при `--lidar-source sim` публикуются подставные расстояния, при `none` все секторы остаются `Unknown`. |
| `camera.pitch`, `camera.yaw` | Последняя успешно применённая команда PWM в координатах команды −1…1. Только при `--servos`, после успешной записи обеих осей. Это заданное положение, а не измеренный угол: обратной связи от сервоприводов нет. |

До первой команды, при выключенных сервоприводах, ошибке PWM, некорректной команде, разрыве соединения и таймауте команд поля камеры равны `NaN`. Настройки инверсии и калибровки меняют PWM, но не систему координат возвращаемой команды. Клиент пока отображает только CPU и батарею; поля камеры доступны в принятом `Telemetry`.

Заряд берётся только из драйвера батареи/UPS, который публикует `capacity`. Питание Raspberry Pi само по себе не даёт процент заряда внешнего аккумулятора. Напряжение и сигнал пониженного питания не превращаются в выдуманный процент. Текущая программа ESP32 принимает команды колёс и не передаёт показания датчиков обратно.

Единицы атрибутов описаны в документации ядра: [thermal sysfs](https://www.kernel.org/doc/html/latest/driver-api/thermal/sysfs-api.html) и [power supply class](https://www.kernel.org/doc/html/latest/power/power_supply_class.html). На Windows системные показатели сервера недоступны и также равны `NaN`; `--video-source test` меняет только видео.

Проверка источников на Raspberry Pi:

```bash
for zone in /sys/class/thermal/thermal_zone*; do
  [ -d "$zone" ] || continue
  printf '%s: ' "$zone"
  cat "$zone/type" "$zone/temp"
done
for supply in /sys/class/power_supply/*; do
  [ -d "$supply" ] || continue
  printf '%s\n' "$supply"
  for attr in type scope present capacity; do
    [ -r "$supply/$attr" ] || continue
    printf '  %s: ' "$attr"
    cat "$supply/$attr"
  done
done
```

Подготовлен отдельный тест чтения sysfs на временных файлах: проверяет единицы, недоступные/повреждённые показания, исчезновение датчиков, выбор батареи, `NaN` и раскладку пакета. Он не требует датчиков, GPIO или GStreamer. Из корня проекта на Linux:

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -Icommon -Irobot \
  tests/test_system_telemetry.cpp robot/systems/rpi/health/system_telemetry.cpp \
  -o /tmp/test_system_telemetry
/tmp/test_system_telemetry
```

Пороги лидара проверяются отдельным тестом без железа и без сокетов:

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -Icommon -Irobot \
  tests/test_obstacle_check.cpp -o /tmp/test_obstacle_check
/tmp/test_obstacle_check
```

Блокировка движения по вердикту (замена команды на `STOP`) проверяется тем же способом,
без железа и сокетов:

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -Icommon -Irobot \
  tests/test_drive_gate.cpp -o /tmp/test_drive_gate
/tmp/test_drive_gate
```

Сборка и запуск этого теста в рамках правки не выполнялись; реальные показания и PWM нужно проверить на Raspberry Pi.

## Лидар и секторы препятствий

Драйвера лидара пока нет — есть готовый каркас, в который его вписывают.

Шесть секторов по 60°, по часовой стрелке от носа робота: `forward`, `forward_right`,
`back_right`, `back`, `back_left`, `forward_left`. Модуль лидара измеряет расстояние до
ближайшего препятствия в каждом секторе **в миллиметрах**; непромеренный сектор остаётся
`NaN` и никогда не превращается в 0 (это читалось бы как препятствие вплотную) или в большое
число (читалось бы как свободный путь).

Разделение ответственности:

| Где | Что делает |
|---|---|
| `robot/systems/rpi/lidar/lidar_reader.cpp` | Свой поток. Измеряет и публикует `LidarDistances`. Единственное место, которое трогает разработчик лидара. |
| `robot/systems/rpi/lidar/lidar_distances.h` | Структура из шести именованных `float`, без логики. |
| `robot/control/safety/obstacle_check.h` | Пороги и чистая функция сравнения. Ни состояния, ни ввода-вывода. |
| `ObstacleState` в `robot/state.h` | Единственный вызов `evaluate()`, хранение последнего вердикта и его возраста. |
| `robot/systems/rpi/link/telemetry_link.cpp` | Только читает готовый вердикт и кладёт в `Telemetry.sectors`. |
| `robot/control/safety/drive_gate.h` | Чистая функция: вердикт + направление → команда, которую реально выполнит привод. |
| `robot/control_loop.cpp` | Читает тот же вердикт и пропускает команду привода через `gateDriveCommand()`. |

Сравнение с порогами выполняется **ровно один раз**, в `ObstacleState::update()`. Если позвать
`evaluate()` где-то ещё, появится вторая копия порогов, и вердикт в телеметрии рано или поздно
разойдётся с тем, по которому робот принимает решения.

Вердикт не только показывается оператору, но и **блокирует движение**. Перед отправкой
кадра на UART `runCommandListener()` прогоняет команду привода через `gateDriveCommand()`
(файл `robot/control/safety/drive_gate.h`): если направление ведёт корпус в сектор с вердиктом
`Red`, команда заменяется на `STOP`. Проверяется тот же опубликованный вердикт, что уходит
в телеметрию, и с тем же порогом устаревания — второй копии порогов нет.

Блокируются только поступательные направления в сторону `Red`-сектора: `FORWARD` и `BACKWARD`
по своему сектору, диагонали — по прямому сектору **или** по своему углу. Развороты на месте
(`LEFT`, `RIGHT`) и `STOP` не блокируются никогда, чтобы зажатый со всех сторон робот мог
отвернуть. `Yellow`, `Green` и `Unknown` движение не останавливают: непромеренный сектор (лидар
выключен или выборка устарела) не должен намертво обездвиживать робота.

Флаг `--obstacle-no-enforce` возвращает прежнее поведение «только телеметрия, без блокировки».

Выборка старше `--lidar-max-age` считается недействительной, и все секторы возвращаются в
`Unknown`. Зависший или умерший поток лидара иначе продолжал бы бесконечно отдавать последний
вердикт, а устаревшее «чисто» — ровно то показание, которое однажды заведёт робота в стену.

Как вписать настоящий драйвер: заменить `readDistances()` в `robot/systems/rpi/lidar/lidar_reader.cpp`
реальными измерениями и добавить открытие/закрытие устройства в двух помеченных местах
`runLidarReader()`. Поток, периодичность и публикация уже написаны, менять их не нужно.

## Автономное исследование

Робот строит карту по лидару и сам едет к ближайшему неисследованному месту.
Запускается кнопкой **Explore** на пульте, карта показывается кнопкой **Map**.

```bash
sudo ./build-pi-fixed/robot --camera 0 --drive-uart --servos
```

SLAM и канал карты работают всегда; отключить — `--no-slam`.

### Как это устроено

| Файл | Что делает |
|---|---|
| `robot/systems/rpi/lidar/scan.h` | Полный оборот лидара в метрах, система робота: x вперёд, y влево. Отдельно от шести секторов — те остаются защитой и не меняются. |
| `robot/control/auto/slam.cpp` | Сопоставление скана с картой: подбирает сдвиг и поворот, при которых оборот лучше всего ложится на уже построенное. Найденное смещение и есть перемещение робота. |
| `robot/control/auto/explore.cpp` | Фронтир — свободная клетка, граничащая с неизвестной. Поиск в ширину от робота по проходимым клеткам, первый найденный фронтир и есть ближайший **по пути**. |
| `robot/control/auto/map_types.h` | Сетка занятости 400×400 по 5 см (20×20 м), лог-шансы в `int8_t`. |
| `robot/systems/rpi/link/map_link.cpp` | Порт 5004: карта дважды в секунду, запрос режима обратно. |

Команда автономии проходит **через тот же `drive_gate`**, что и команда
оператора. Автономия не знает, что гейт существует, и обойти его не может.

### Ограничения, о которых надо знать

**Одометрии нет.** Ни энкодеров, ни IMU — положение берётся только из
сопоставления сканов. Отсюда два следствия:

- **Длинный пустой коридор ломает SLAM.** Скан вдоль ровной стены одинаково
  хорошо ложится в любом месте вдоль неё, и робот не понимает, сколько проехал.
  Работает там, где есть углы, дверные проёмы и мебель.
- **Дрейф не исправляется.** Замыкания петли нет: проехав круг по этажу, робот
  не сведёт начало с концом. Это честный предел одного файла scan matching, а не
  недоделка — исправление это уже оптимизация графа поз.

Когда сопоставление плохое (`match_score` ниже 0.22), скан отбрасывается
целиком: поза остаётся прежней, карта не трогается. Записать скан не в том месте
— необратимо испортить карту. На пульте это видно надписью **SLAM lost**.

**`--robot-radius` надо замерить.** По умолчанию 20 см — это половина ширины
корпуса плюс запас. Планировщик вычёркивает клетки ближе этого расстояния к
стене, поэтому заниженное значение проведёт маршрут в проём, куда робот не
влезет.

### Переключение режимов

- **Explore** на пульте включает автономию, повторное нажатие выключает.
- **Любая команда движения оператора мгновенно возвращает ручной режим.** Взять
  управление можно не глядя на кнопки — просто нажать клавишу движения.
- Кнопка показывает то, что робот **делает**, а не то, что у него запросили:
  режим приходит в каждом кадре карты.
- **Потеря связи автономию не останавливает** — робот продолжает исследовать.
  Манёвр отхода назад при обрыве связи в этом режиме не выполняется, иначе он
  боролся бы с планировщиком. Единственный способ остановить уехавшего робота —
  переподключиться и нажать Stop либо снять питание.

### Проверка без робота

```bash
./build-win/robot --lidar-source sim --video-source none
```

Виртуальная комната 5×4 м с дверным проёмом: SLAM строит карту, канал 5004
отдаёт её, пульт рисует. Робот в симуляции только вращается на месте, так что
проверяется вся цепочка, но не езда.

Проверка самого SLAM на синтетической траектории с известным ответом:

```bash
c++ -std=c++17 -O2 -Wall -Wextra -Wpedantic -Icommon -Irobot   tests/test_slam.cpp robot/control/auto/slam.cpp -o /tmp/t -pthread && /tmp/t
```

## Протокол

Оба TCP-соединения открывает Windows; Raspberry Pi слушает. На каждом соединении обслуживается один клиент.

| Порт | Данные | Размер / период |
|---|---|---|
| TCP 5001 | Windows → Raspberry Pi: `DesiredState` | 16 байт / 5 мс в текущем исходнике клиента |
| TCP 5002 | Raspberry Pi → Windows: `Telemetry` | 22 байта / 100 мс |
| UDP 5003 | Raspberry Pi → Windows: RTP/H.264 | По частоте камеры |

Структуры из `common/protocol.h` передаются целиком, без заголовков и преобразования чисел в network byte order. Контракт: **little-endian, IEEE-754 float32**. Windows x64 и Raspberry Pi OS используют совместимое представление. Размеры и смещения закреплены `static_assert`.

- `DesiredState`: direction @0 (1 байт), padding @1–3, speed @4, pitch @8, yaw @12.
- `Telemetry`: cpu_temp @0, battery_level @4, точки @8…151 (12 × 12 байт: angle, distance, intensity), camera.pitch @152, camera.yaw @156.
- Недоступные поля телеметрии — IEEE-754 quiet NaN. Получатель проверяет каждое поле через `isfinite`; ноль остаётся допустимым реальным показанием. Для `DesiredState` NaN по-прежнему запрещён.
- Три байта padding после direction — часть старого формата; удалять их нельзя.
- Сервер собирает частичные TCP-чтения и дописывает частичные отправки. Неполная/отсутствующая команда за 500 мс разрывает соединение; дедлайн отправки телеметрии — 1 с. После разрыва сервер снова принимает клиента.
- В Windows переподключение запускается после ошибки или закрытия TCP. Таймаут после частичного чтения/отправки закрывает соединение, чтобы восстановить границы пакетов при переподключении. Таймаут до первого байта сохраняет соединение. HUD очищает устаревшую телеметрию примерно через 1 с.

## Управление

| Ввод | Действие |
|---|---|
| W A S D | Движение пока клавиша удерживается, STOP при отпускании |
| W+D, W+A, S+D, S+A | Диагонали: внешнее колесо на полной команде, внутреннее на 50 % |
| Стрелки | Движение по переключению: повтор той же стрелки даёт STOP; диагоналей нет |
| Мышь | Pitch/yaw камеры, диапазон -1…1 |
| Левый клик | Захват мыши |
| Esc | Освободить мышь |
| F11 | Полноэкранный режим |
| POWER | Мощность команды |

WASD и стрелки записывают общее желаемое состояние; последняя команда имеет приоритет.

Противоположные клавиши гасят свою ось: `W+S` и `A+D` дают STOP, `W+A+D` — обычный FORWARD. Потеря фокуса окном отпускает все клавиши и останавливает робота.

Диагонали замедляют колесо со стороны поворота, поэтому задним ходом робот рулит как автомобиль: `S+D` уводит корму вправо, то есть корпус разворачивается против часовой стрелки — в сторону, противоположную отдельной команде RIGHT. Коэффициент внутреннего колеса — `kDiagonalInnerFactor` в `robot/systems/rpi/drive/drive_controller.h`.

| Команда | `Direction` | Колёса при `speed = 1.0` |
|---|---|---|
| Вперёд-вправо | 5 | `R:50%\|L:100%` |
| Вперёд-влево | 6 | `R:100%\|L:50%` |
| Назад-вправо | 7 | `R:-50%\|L:-100%` |
| Назад-влево | 8 | `R:-100%\|L:-50%` |

Значения `Direction` 5…8 новые: робот, собранный со старым `common/protocol.h`, считает такие пакеты некорректными и разрывает соединение. Размер `DesiredState` не изменился (16 байт), пересобрать нужно обе стороны.

## Диагностика на устройстве

Проверка камеры отдельно от сервера (сначала остановите `robot`):

```bash
rpicam-vid --camera 0 --nopreview --timeout 5000 --codec h264 --inline \
  --width 1280 --height 720 --framerate 30 --output /tmp/imx219.h264
```

Проверка необходимых GStreamer-элементов:

```bash
gst-inspect-1.0 fdsrc
gst-inspect-1.0 h264parse
gst-inspect-1.0 rtph264pay
gst-inspect-1.0 udpsink
```

Если TCP работает, а изображения нет, проверьте строку `[video]` с адресом назначения, UDP-порт и Windows Firewall. Ошибки `rpicam-vid` выводятся в stderr сервера; ошибки Windows-видеоприёмника — в `control.log` рядом с `control.exe`.

Изменения управления сервоприводами подготовлены без компиляции и аппаратной проверки. Сборку, направления осей и пределы хода нужно проверить на Raspberry Pi с установленной камерой.
